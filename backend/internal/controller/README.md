# controller

## Overview
`bezisync controller`: the leader-elected loop that turns the desired state the API writes into running workloads and evidence. Each tick it prepares source/sink artifacts, applies each deployed pipeline's workload through its runtime driver, observes health and metrics, derives the verdict with `domain.Derive`, and writes `pipelines.status`; it then evaluates alerts, runs queued jobs (`restart`, `cleanup`, `snapshot`, `notify`) and periodic maintenance. It also holds the logic behind `bezisync uninstall`. Business rules come from [services](../services/README.md); drivers from [runtime](../runtime/README.md).

## Interface
- `[controller.go:Main]` / `[controller.go:New]` / `[controller.go:Controller]` — the process; tick from `config.Get().ControllerTickSeconds`.
- `[controller.go:RunForever]` — competes for `pg_try_advisory_lock(LeaderLock)` and leads while holding it; `[controller.go:LeaderLock]` is shared with the Python controller.
- `[controller.go:TickOnce]` — one round: reconcile every deployed pipeline, `EvaluateAlerts`, `RunJobs(ctx, 10)`, maintenance every 10 min. On the first tick after start it also logs a warning naming running workloads whose config hash would change (`[controller.go:Controller.reportHashDrift]`).
- `[controller.go:Reconcile]` — converge and record one pipeline.
- `[controller.go:EvaluateAlerts]` — `services.EvaluateProject` per project, one transaction each.
- `[controller.go:CarriedStatus]` — status keys written outside the observe loop that each tick keeps: `counters`, `source_impact`, `events_per_second`, `forced`, `scheduled_snapshot`, `schema_pending_breaking`, `canary`, `transform_drift`.
- `[controller.go:ParseHealth]` — SmallRye health: 200 + `UP` up, 503 down, anything else unknown (nil).
- `[controller.go:EnsureStateSchema]` — creates Debezium's state schema (`compiler.StateSchema`) in the state database.
- `[controller.go:CanaryPoll]`, `[controller.go:CanaryTailTimeout]`, `[controller.go:Identity]` (hostname-pid, used in job locks).
- `[jobs.go:RunJob]` — dispatches `restart`, `cleanup`, `snapshot`, `notify`; `[jobs.go:RunJobs]` claims and runs due jobs; `[jobs.go:Defer]` reschedules without counting an attempt.
- `[uninstall.go:Plan]` / `[uninstall.go:Uninstall]` with `[uninstall.go:PlanItem]`, `[uninstall.go:UninstallEntry]` — list, then remove, every live pipeline's workload, source artifacts and offsets.
- `[flinkcdc.go:observeFlink]` — Flink CDC evidence from the helper's `/q/health` and `/bz/status`, mapped onto `domain.Metrics` (`flinkMetrics`), a DOWN reason (`flinkDown`) and `status.flink` (`flinkStatus`).
- `[flinkcdc.go:Controller.flinkPhase]` — each tick of a Flink CDC pipeline with `desired_state = running` and a deployed version, applies `services.FlinkPhaseStep` (shrink a custom cluster after the first copy, or revert a failed streaming shape; `failed` is the verdict or the helper phase `failed`/`config_error`, `auto` is the project policy `ShrinkAuto`) and records the resize as an audit event with actor `controller`; the new shape takes effect on the next tick through its config hash.

## Invariants
- One leader: the lock is held on a dedicated connection pinged with `SELECT 1` every tick (`[controller.go:Controller.lead]`); losing it ends leadership.
- `Reconcile` locks the pipeline row with `FOR UPDATE SKIP LOCKED` and only acts on non-deleted pipelines with a deployed version (`[controller.go:Reconcile]`); at most 8 pipelines reconcile concurrently and a panic is recovered and logged (`[controller.go:TickOnce]`).
- Artifacts are prepared once per deployed version (`artifacts.prepared_version_id`); a sink result with outcome `failed` fails the apply (`[controller.go:Controller.prepareIfNeeded]`). Flink CDC refreshes the tables' columns first (`services.RefreshFlinkColumns`). After the prepare, before the compile, a Flink CDC pipeline's next start is planned (`services.EnsureFlinkStartPlanned`, ADR 0012): an error is the apply error, and the pipeline doesn't start.
- Health is evidence-based: the verdict comes only from `domain.Derive`; an apply error is prepended as `apply_failed` unless streaming, and a pipeline still deploying 2 min after `DeployedAt` with an apply error becomes failed/down.
- `[controller.go:Controller.storeStatus]` rebuilds `status` from scratch keeping only `CarriedStatus` keys; any new key written outside the observe loop must be added there or the next tick drops it. A lifecycle change records a `pipeline.<lifecycle>` event with `NotAudit: true` (first 3 reasons). `source_impact`, `flink` and the position note are written after it on the same tick; `flink` is not carried, so it is rebuilt from each tick's `/bz/status` answer.
- Per engine (`services.EngineOf`): Flink CDC is observed through the helper on `connectors.DefaultHealthPort` (`[flinkcdc.go:observeFlink]`; its DOWN reason reaches `domain.Derive` as `EngineDown`) and its latency target is at least 1.5 × the larger of the effective commit and freshness intervals (`spec.FlinkCDC.Effective()`); Debezium reads `/q/health` on `connectors.HealthPort` and metrics on `:9404/metrics`, and its latency target is at least 1.5 × the sink's `connectors.DeliveryDelay` (`[controller.go:Reconcile]`). Engine settings are validated in services and the compiler; the controller only reads their effective values.
- Each schema check also writes `schema_pending_breaking` and `transform_drift` (findings for the deployed transform steps against the schema just read) (`[controller.go:transformDrift]`, on the pipeline's engine, with each column's nullability).
- `[controller.go:Controller.checkPosition]` reads the stored Postgres LSN after each fresh source probe, writes `last_lsn`, and sets `position_regressed` when it is lower than the previous `last_lsn`. Both keys are in `CarriedStatus`, so ticks without a probe keep them and the alert stays raised until the next probe.
- Throttles: source probe every 30 s (`probeEvery`), metric samples at most every 15 s (`[controller.go:Controller.recordSample]`, rate from counter deltas, negative deltas dropped), schema check every `SchemaCheckSeconds` and only while streaming or snapshotting for sources with `TracksSchema` (`[controller.go:Controller.trackSchema]`), canary (policy `DeliveryCanary`, streaming, both connectors support it) every `CanaryIntervalSeconds`, polled every `CanaryPoll`, `ok: false` after `CanaryTimeoutSeconds`; a new canary is written only while none is pending (`[controller.go:Controller.canary]`). A timed-out canary moves its `sent_at` to `lost_sent_at` (which the `delivery_unverified` alert names), leaves `pending`, and the next canary is written when due; a verified canary clears `lost_sent_at`.
- Only non-agent runtimes get `runtimes.last_seen_at` from the controller, and only when the driver answered; agent runtimes are refreshed by the agent's own poll.
- Jobs are delivered at least once and every handler is idempotent. Claiming uses `FOR UPDATE SKIP LOCKED` ordered by `run_after`, sets `running`, `locked_by`, `locked_at` and increments `attempts` (`[jobs.go:RunJobs]`). The handler runs in a savepoint whose writes are kept even when it then fails; failures retry with `[jobs.go:backoff]` (5 s × 2^attempts, so the first retry waits 10 s, capped at 300 s) until `max_attempts`, then `failed`; a `Defer` requeues at `Until` and gives the attempt back. `services.Retry` errors are not logged as errors. `[jobs.go:Controller.runJob]` holds its job's row lock (`FOR UPDATE`) for the whole handler: that lock is the lease ([ADR 0003](../../../docs/adr/0003-job-reclaim.md)). Each `RunJobs` first runs `[jobs.go:Controller.reclaimJobs]`: a `running` job claimed more than `[jobs.go:ReclaimGrace]` (1 min, by the controller's clock) ago whose row it can lock (`SKIP LOCKED`) has no live owner; a `snapshot` becomes `failed` (never re-sent on its own), any other job `queued` now, or `failed` at `max_attempts`, with an "Interrupted" error and an audit event `job.reclaimed` (actor `controller`). Recovery waits for Postgres to drop the dead owner's connection (immediate when the process dies, TCP keepalive after a node crash).
- `[jobs.go:jobSnapshot]` waits (`services.Retry`) until the pipeline is streaming or snapshotting, defers to the snapshot window unless `ignore_window` (status `scheduled_snapshot`), marks queued snapshot jobs whose tables it covers `done` with `superseded_by`, then sends an `execute-snapshot` signal (default mode `incremental`) and records a `pipeline.snapshot` event (`NotAudit`). On an engine without `recopy_table` (Flink CDC) it sends nothing and finishes `done` with `skipped`.
- `[jobs.go:jobCleanup]` deletes the workload and waits up to 30 × 2 s for `missing`; then, only for a pipeline with a deployed version, source cleanup, destination drop only with payload `drop_destinations`, `SinkReleaser` helpers always, offsets cleared, and Flink CDC saved positions dropped. A failed artifact step sets lifecycle `cleanup_failed`, else `deleted`; errors loading connections or clearing offsets fail the job instead. It records a `pipeline.cleanup` event (`NotAudit`). `[jobs.go:jobRestart]` only deletes the workload; the next reconcile recreates it.
- `[uninstall.go:Uninstall]` covers every pipeline whose lifecycle is not `deleted`: it sets `desired_state = paused`, lifecycle `deleting` and `deleted_at`, then runs the cleanup handler with an in-memory job (no `jobs` row) in its own transaction, inside a savepoint (`[uninstall.go:runSavepoint]`) that is rolled back on error — the `deleting` mark is still committed and the entry reports `OK: false`; pipelines without a runtime are just marked deleted. `[uninstall.go:Plan]` changes nothing.

## Side Effects
- DB writes: `pipelines` (status, lifecycle, health, artifacts via `services.SavePipeline`; `desired_state`/`deleted_at` in uninstall), `metric_samples` (resolution 0), `schema_changes`, `jobs` (claim, result, superseded snapshots), `runtimes.last_seen_at`, events via `services.Record` (`NotAudit` lifecycle, cleanup and snapshot events; audited Flink CDC resize events with actor `controller`); reads offsets (`services.ReadOffsets`) and clears them (`services.ClearOffsets`, `services.DropSavedPositions`).
- Maintenance every 10 min: `services.EnforceMetricRetention`, `services.MaybeSendTelemetry` (may call out), `services.ExpireSavedPositions`.
- Runtimes: `Apply`/`Delete`/`Observe`/`Logs`/`HTTPGet` on Docker, Kubernetes or agent drivers.
- Sources and sinks over the network: `Prepare`/`PrepareSink`, `Discover`, source impact probes, canary writes (`WriteCanary`) and reads (`Tail`, only where `services.CanaryRuns`: never on Flink CDC pipelines), snapshot `Signal`, cleanup.
- Separate connections: the leader-lock connection to `DatabaseURL` and, at start, one to the state database (`EffectiveStateDatabaseURL`); env via `config.Get()` only.
- Goroutines: up to 8 reconcilers per tick; logs via `bezisync.controller`.
